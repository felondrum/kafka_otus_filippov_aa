# Проект: «Разработка событийно-ориентированной платформы для обработки звонков банковского колл-центра на базе Apache Kafka»

## Краткое описание проекта

Разработка платформы для обработки звонков банковского колл-центра с использованием событийно-ориентированной архитектуры на Apache Kafka. Система обеспечивает потоковую обработку входящих звонков, антифрод-мониторинг, транскрибацию и суммаризацию диалогов с симуляцией LLM, а также построение аналитической отчетности в реальном времени.

## Бизнес-смысл

Банковский колл-центр ежедневно обрабатывает тысячи звонков. Руководству необходима прозрачность качества обслуживания, контроль мошеннических действий и аналитика для улучшения клиентского опыта. Существующие решения работают в пакетном режиме (отчеты раз в сутки), что не позволяет оперативно реагировать на негативные сценарии (например, эскалацию конфликта или фродовые паттерны).

**Цель** — построить систему, которая:

- Обрабатывает звонки в реальном времени.
- Автоматически классифицирует проблематику обращений (потери карт, вопросы по кредитам, жалобы).
- Выявляет мошеннические паттерны (частые звонки с одного номера, подозрительные сценарии).
- Создает суммаризацию диалогов для архивации и быстрого поиска.
- Предоставляет менеджерам дашборды с актуальной статистикой (NPS, загрузка агентов, тональность обращений).
- Хранит полную историю с привязкой метаинформации к расшифровкам для аудита.

## Верхнеуровневая архитектура

Система построена по принципам событийно-ориентированной архитектуры (Event-Driven Architecture) с использованием хореографии — микросервисы не взаимодействуют напрямую, а обмениваются событиями через брокер сообщений.

### Схема взаимодействия компонентов

1. **Входная точка — сервис приема звонков (call-processor):**

   - Принимает REST-запросы о завершении звонка (длительность, агент, NPS-оценка).
   - Валидирует входящие данные и отправляет событие в Kafka.
   - Управляет жизненным циклом топиков (создание, настройка партиций, репликаций).
   - Реализует механизмы надежной доставки (retries, dead letter queue, идемпотентность).

2. **Антифрод-модуль (fraud-detector):**

   - Читает поток звонков и применяет потоковую обработку (Kafka Streams).
   - Вычисляет паттерны: количество звонков с одного номера за временное окно, аномальная длительность, подозрительная тональность.
   - При обнаружении подозрительной активности отправляет алерты в отдельный топик.
   - Хранит состояние каждого номера в локальном State Store для быстрых запросов.

3. **Модуль транскрибации и суммаризации (transcription-analyzer):**

   - Слушает события завершенных звонков.
   - Симулирует получение транскрипции диалога (аудио → текст) с параметрами качества и языка.
   - Симулирует работу LLM для извлечения сути: проблема, решение, эмоциональный фон (сентимент), срочность.
   - Обогащает данные профилем клиента (сегмент, риск-уровень) через джойн потока и таблицы.
   - Управляет метаинформацией звонка (жизненный цикл статусов: `PENDING` → `TRANSCRIBING` → `SUMMARIZING` → `COMPLETED`).
   - Сохраняет финальные данные в PostgreSQL (две связанные таблицы: метаданные и расшифровки).

4. **Сервис отчетности и аналитики (reporting-nps):**

   - Реализует паттерн CQRS: команды пишутся в Kafka, запросы читаются из PostgreSQL.
   - Предоставляет REST API для получения аналитики: средний NPS по агентам, распределение обращений по сегментам, статистика тональности.
   - Поддерживает интерактивные запросы к State Store Kafka Streams (без обращения к БД) для получения актуального статуса звонка.
   - Агрегирует данные за период и кэширует результаты.

## Мониторинг и инфраструктура

- Kafka кластер из 3 брокеров в режиме Kraft (без ZooKeeper).
- Schema Registry для централизованного хранения и валидации Avro-схем.
- Kafdrop для визуализации топиков, партиций, реплик и потребителей.
- PostgreSQL как основное хранилище для аналитики и архивации.
- Kafka Connect с JDBC Sink коннектором для автоматической записи записей в БД.
- Prometheus для сбора метрик (лаг потребителей, throughput, ошибки).
- Grafana для визуализации дашбордов (состояние кластера, загрузка сервисов, статусы звонков).
- ksqlDB для интерактивных SQL-запросов к потокам (дополнительный аналитический слой).

## Стек технологий

### Языки и фреймворки

- Java 21+ (основной язык разработки).
- Spring Boot 3 (REST API, конфигурация, интеграция с Kafka).
- Spring for Apache Kafka (аннотации, контейнеры, транзакции).
- Spring Data JPA (работа с PostgreSQL).

### Брокер и потоковая обработка

- Apache Kafka (брокер сообщений, кластер из 3 узлов).
- Kafka Streams (потоковая обработка, DSL и Processor API).
- Kafka Connect (JDBC Sink коннектор с трансформациями).
- ksqlDB (аналитические запросы в реальном времени).

### Сериализация и схемы

- Apache Avro (сериализация событий, все схемы хранятся в Schema Registry).
- Confluent Schema Registry (валидация совместимости, управление версиями).

### Хранилища

- PostgreSQL 15 (реляционная БД, связанные таблицы `call_metadata` и `call_transcriptions`).
- RocksDB (встроенное хранилище состояний Kafka Streams).

### Контейнеризация и оркестрация

- Docker & Docker Compose (локальное развертывание всех компонентов).
- Совместимость с Mac Apple Silicon (m1) (платформа `linux/arm64/v8`).

### Мониторинг и визуализация

- Kafdrop (UI для управления Kafka).
- Prometheus (сбор метрик).
- Grafana (дашборды, алерты).

### Тестирование

- Testcontainers (интеграционные тесты с реальными зависимостями).
- Embedded Kafka (unit-тесты для потребителей и продюсеров).
- JUnit 5, AssertJ, Mockito (стандартный стек тестирования).

## Требования к данным и топикам

### Топики Kafka (все с репликацией 3, партиции 6)

| Топик | Тип | Ключ | Формат | Описание |
|---|---|---|---|---|
| `calls.completed` | Stream | `callId` | Avro | Завершенные звонки |
| `calls.metadata` | Compacted Table | `callId` | Avro | Метаинформация звонков (жизненный цикл) |
| `calls.fraud-alerts` | Stream | `phone` | Avro | Алерты антифрода |
| `transcription.raw` | Stream | `callId` | Avro | Сырая транскрипция диалога |
| `transcription.summary` | Stream | `callId` | Avro | Суммаризация от LLM |
| `transcription.enriched` | Stream | `callId` | Avro | Обогащенная суммаризация с профилем клиента |
| `calls.dlq` | Stream | `callId` | JSON | Dead Letter Queue для битых сообщений |
| `customers.profile` | Compacted Table | `phone` | Avro | Профили клиентов (загружаются админами) |

### Схема данных PostgreSQL

- **call_metadata** — метаинформация звонка (`call_id`, `phone`, `duration`, `agent_id`, `nps_score`, `segment`, `risk_level`, `priority`, `status`, `total_calls`, `last_updated`).
- **call_transcriptions** — расшифровка диалога (`call_id` (FK), `transcription_text`, `sentiment`, `urgency`, `problem`, `solution`, `confidence`).
- **view v_full_call_info** — представление, объединяющее обе таблицы для отчетности.

## Функциональные требования к микросервисам

### 1. call-processor (API Gateway + Producer)

- REST `POST /api/calls` — принять звонок, валидировать.
- При старте создать топики через Admin API (если не существуют).
- Настроить ACL (пользователи с правами записи/чтения).
- Обеспечить идемпотентную отправку (`enable.idempotence=true`, `acks=all`).
- Перехватывать ошибки и отправлять в DLQ.
- Отдавать статус операции (202 Accepted / 400 Bad Request).

### 2. fraud-detector (Streams)

- Читать `calls.completed`.
- Фильтровать короткие звонки (< 5 сек).
- Вычислять частоту звонков с одного номера за 1 минуту (sliding window).
- При превышении порога (5 звонков/мин) отправлять алерт в `calls.fraud-alerts`.
- Использовать Processor API для детекции эскалации (3 негативных NPS за день).
- Хранить счетчики в State Store (RocksDB) с автоматической очисткой по таймеру.
- Гарантировать exactly-once обработку.

### 3. transcription-analyzer (Producer + Streams + Consumer)

- **Producer часть:** генерировать транскрипцию (симуляция текста из длительности), отправлять в `transcription.raw`.
- **Streams часть:** читать транскрипции, извлекать ключевые слова (card, loan, fraud), формировать структурированную суммаризацию (problem, solution, sentiment, urgency).
- **Обогащение:** джойнить суммаризацию с `customers.profile` (KTable) по `phone` для получения сегмента и `risk_level`.
- **Управление метаданными:** создавать/обновлять записи в `calls.metadata` (статусы PENDING → TRANSCRIBING → SUMMARIZING → COMPLETED).
- **Consumer часть:** слушать `transcription.enriched`, сохранять в PostgreSQL (dual-write: через ручной Consumer + Kafka Connect JDBC Sink).

### 4. reporting-nps (Consumer + REST)

- Читать `calls.metadata` и `transcription.enriched` для обновления аналитики.
- Сохранять агрегированные данные в PostgreSQL (ежедневная статистика по агентам, сегментам, тональности).
- Предоставлять REST API:
  - `GET /api/reports/daily` — дневная сводка (NPS, кол-во звонков).
  - `GET /api/reports/agent/{id}` — статистика по агенту.
  - `GET /api/metadata/{callId}` — актуальный статус звонка (из State Store).
  - `GET /api/metadata/status/{status}` — звонки по статусу.
  - `GET /api/sentiment/distribution` — распределение тональности за период.

## Нефункциональные требования

- **Надежность:** обработка ошибок через DLQ, повторные попытки при временных сбоях.
- **Масштабируемость:** каждый микросервис должен горизонтально масштабироваться (до 3+ экземпляров).
- **Тестируемость:** покрытие ключевых сценариев интеграционными тестами (Testcontainers).
- **Демонстрация:** возможность показать рабочий стенд за 10 минут (скрипты с curl, преднастроенные дашборды).
- **Мониторинг:** обязательное логирование, метрики (lag, ошибки, throughput), алерты в Grafana.
- **Безопасность:** базовая аутентификация на Kafka (SASL/PLAIN) и ACL для разделения прав сервисов.
- **Совместимость:** полная поддержка Mac Apple Silicon (m1) через Docker.

## Критерии приемки (Definition of Done)

1. Все 4 микросервиса поднимаются локально через `docker-compose up`.
2. В Kafdrop видны все топики, партиции, реплики и активные потребители.
3. Отправка звонка через REST API приводит к полной цепочке обработки (метаданные → транскрипция → суммаризация → PostgreSQL) менее чем за 30 секунд.
4. При симуляции фрода (6 звонков с одного номера за 30 сек) в топике `calls.fraud-alerts` появляется сообщение.
5. В PostgreSQL корректно заполнены обе связанные таблицы с валидными Foreign Key.
6. REST API `/api/metadata/{callId}` возвращает актуальный статус звонка (включая промежуточные состояния).
7. В Grafana отображаются:
   - Lag потребителей (не более 100 для всех групп).
   - Throughput (сообщений/сек) для каждого топика.
   - Статусное распределение звонков (PENDING, TRANSCRIBING, COMPLETED).
8. Любой из сервисов можно остановить и перезапустить без потери данных (State Store восстанавливается).
9. Интеграционные тесты (Testcontainers) проходят успешно в CI-среде.
10. Документация API доступна через Swagger (OpenAPI 3) для каждого сервиса.
